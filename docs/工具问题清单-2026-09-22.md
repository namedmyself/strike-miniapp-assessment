### 核查中的自我修正

1. **P0-4 的机制我没能复现**。原文写「appservice context 失效时求值挂满 15s」，
   但实测传**不存在的 `context_id`** 是**快速失败（0.245s）**，报
   `{"code": -32000, "message": "Cannot find context with specified id"}`。
   所以「什么条件下会挂 15s」**仍未查清** ——
   **现象是硬的（15.01s + samples 空），但根因解释只是推断**。
2. **P1-7 的修复建议属于过度**。已从「统一补 `additionalProperties: false`」
   改为**「不建议改」**，理由见该条目。
3. **P0-4 / P0-5 的机制已确证，但「实战损害」仍无直接记录**（21:05 现场对照后更新）。
   它们是真实缺陷（现象与机制**都已当场复现**），但**没有任何记录表明它们实际导致了错误决策** ——
   与 P0-1（漏报高危漏洞）、P0-2（按文档执行就溢出）不在一个量级。
   保留修复是因为**成本低、风险低**，但不应与 P0-1 并列为「阻断级」。
4. **P1-7 是我自己造成的**：我传了 `timeout_seconds`（正确名是 `timeout`）。
   把「我用错了参数名」记成「工具的缺陷」，是**归因错误**。

### 现场对照实证（2026-09-22 21:05，真实运行时）

> 手法：把「修复前的表达式」与「修复后的表达式」**同时**丢进真实小程序运行时求值做对照。
> 全程只读，不改运行时状态。脚本：`output/verify_route_claim_live.py`。
> 这比回溯日志硬 —— 因为它是**当场重演**，不依赖当时的记录是否完整。

**环境事实（实测探针）**

| 上下文 | 探针 | 值 |
|--------|------|-----|
| page-frame | `typeof globalThis.__wxRoute` | **不存在** |
| page-frame | `window.__routeNavigator.fetchConfigJson` | 存在 |
| appservice（`runtime_context`） | `typeof window` | **不存在** |
| appservice（`runtime_context`） | `typeof getCurrentPages` | 存在 |
| appservice（`frames_bridge`） | `typeof window.__as` | 存在（由桥构造） |

**P0-5 对照：page-frame 读路由**

| 版本 | 表达式 | 实测结果 |
|------|--------|---------|
| 修复前 | `String(globalThis.__wxRoute \|\| '')` | `""` |
| 修复后 | `PAGE_ROUTE_EXPR` | `"pages/other/tzs/collect"` |

→ **当场复现**。旧表达式在 page-frame 里**必然**返回空串（该全局不存在），
所以 `snapshot.route` 恒空是**必然而非偶发**。**P0-5 确证为真缺陷，非过度修正。**

**P0-4 对照：appservice 读路由（行为随模式分叉）**

| appservice 模式 | `window` 存在 | 修复前单点写法 | 修复后降级链 |
|-----------------|--------------|---------------|-------------|
| `runtime_context`（`find_appservice` 默认选中） | ❌ | `""` 空串 | `{route:"pages/other/tzs/collect", via:"globalThis.getCurrentPages"}` |
| `frames_bridge` | ✅ | `"pages/other/tzs/collect"` | `{route:"pages/other/tzs/collect", via:"window.__as.getCurrentPages"}` |

→ **当场复现**。默认路径下 appservice **没有 `window`**，旧单点写法
（`window.__as.getCurrentPages()`）必然取不到值；只有降级到 `frames_bridge`
（桥把 `window.__as` 构造出来）时才碰巧能用。这解释了问题的**间歇性**，
也解释了 `samples: []` + `route: ''` 的来源。**P0-4 确证为真缺陷。**

**旁证：`__wxRoute` 的值是陈旧的**

appservice 里实测 `globalThis.__wxRoute = "pages/other/tzs/success"`，
而同一时刻真实路由是 `"pages/other/tzs/collect"`。
→ 旧代码若依赖它兜底，会读到**错误路由** —— 比返回空串更危险（空串至少看得出读失败）。
这也反证了「改用 `getCurrentPages()`」的方向是对的。

**仍未复现的部分（如实记录）**

P0-4 原始现象里的 **`elapsedSeconds: 15.01`（挂满 CDP 超时）没能复现**。
实测传不存在的 `context_id` 是**快速失败**（0.245s，`-32000 Cannot find context with specified id`）。
所以：「读不到路由」已确证；「什么条件下会挂满 15s」**仍待查**。

**核查中修掉的一个「我自己引入」的瑕疵**

`APPSERVICE_ROUTE_EXPR` 早期把 `via` 硬编码为 `'window.__as.getCurrentPages'`，
在 `runtime_context` 模式下会**误报**（真实命中路径是 `globalThis.getCurrentPages`）。
已改为跟随 `gname` 动态标注；现场验证 `via` 现正确显示 `globalThis.getCurrentPages`。
→ 这类问题**不属于原有缺陷**，是修复过程中新引入的尾巴，必须清理干净 ——
否则「修 bug 引入 bug」正好坐实了「过度修正」。

- 增加 **高熵字符串启发式**：长度 ≥ 12、字符集混合、香农熵 > 3.5 的裸字符串标记为 `possible_hardcoded_secret`。
- 把 `PII_FIELD_RE` / `AUTH_FIELD_RE` 接入 storage 扫描的 key 匹配。

**现象**

1. **`route: ""` + `stable: false`** —— 工具判定"导航失败"，实际导航成功。调用方会误判。

**根因（`runtime_session.py:2222-2237`、`:2239-2268`）**

问题 A：`current_route()` 走的是 `window.__as` 桥 / `globalThis` 路径，**与 `runtime_eval_appservice` 不是同一条路径**。后者能正确拿到路由，前者返回 `""`。两套读路由的实现不一致，`current_route()` 这条是坏的。

    samples.append(...)

`timeout=8` 时，**循环外那一次** `current_route()` 若阻塞约 15s，
`time.time() < deadline` 直接为假、循环体一次都不执行 → 实测
`elapsedSeconds: 15.01` 且 `samples: []`，与现象**完全吻合**。

> ✅ **复现状态（2026-09-22 21:20 两个子问题全部复现）**

### P1-6　`get_request_detail` 的请求/响应头采集不完整且不稳定

### P1-7　未知参数被**静默忽略**，与"严格 schema"的既有认知矛盾

**发现时间**：2026-09-22（本轮修 P0-4 时顺手撞到）

**现象**

本项目此前两次踩坑（P0-2 / P0-3）都是因为 `additionalProperties: false` **拒收**未声明的参数，

**全部 69 个工具都是宽松模式，没有任何一个是严格模式。**

**服务端一致地宽松** —— 未知键被静默丢弃，从不报错。

> ✅ **矛盾已解（2026-09-22 21:20 实测确认）**
>
> 本清单 P0-2 / P0-3 记录的是**报错**：
> ```
> → InputValidationError: additionalProperties: false 不接受 excludeStatic / compact
> ```
> 而服务端审计 + 直连实测都表明**从未有过这个约束**。现在实验给出了答案：
>
> | 实验 | 结果 |
> |------|------|
> | 直连（`wxmcp.py`）传 `nonexistent_param=123` | **不报错**，正常执行（`ok:false` 只因读不到路由） |

> 当年的 `InputValidationError` **只能来自 MCP 客户端侧**

> 补上 `additionalProperties: false` 会让**直连也变脆**，是纯粹的负收益。
>
> 遗留：「参数名写错没有可靠反馈」这个问题依然存在 —— 缓解手段是**返回值回显**
> （如 `timeoutSeconds`），而不是改 schema。

**修复建议：不建议改**（2026-09-22 二次核查后**撤回**原先的建议）

原先我建议「统一补 `additionalProperties: false`」，**这个建议是过度的，撤回**。理由：

1. **没有实战损害证据**。所谓「踩坑」是我自己传错了参数名（`timeout_seconds` vs `timeout`），
   属于**调用方失误**，不是工具缺陷。把归因错误记成缺陷会误导后续决策。
2. **改严格会破坏现有行为**。当前任何「多传一个参数」的调用都能跑；补上
   `additionalProperties: false` 后同样调用会**直接报错** ——
   这是把一个无害的宽松行为换成可能中断流程的严格行为。**风险大于收益。**
3. **宽松是 FastMCP 的默认行为**，大量 MCP 服务如此。调用方（LLM）本就不该依赖
   「多传参数会报错」这个假设。
4. **成本已经在别处付掉了**：真正让问题可见的是**返回值回显**
   （`wait_route_stable` 的 `timeoutSeconds`）—— 本轮正是靠它发现参数名传错的。
   这比改 schema 更轻、更安全。

**如果将来真要改进**，优先级应是：

1. （可选，低风险）在包装层把未消费的 `kwargs` 回显为 `ignoredParams` ——

2. （**不建议**）统一补严格模式 —— 破坏性变更，需先确认没有调用方依赖宽松行为。

**当前处置**：仅保留 `scripts/audit_tool_schema.py` 作为**观察工具**（离线、不改运行时行为），
记录「69/69 宽松」这一事实，**不修改任何工具的 schema**。

### P2-1　缺"批量路由遍历采集"一等能力（**本次直接导致流程被中断**）

#### ✅ 修复结论（v2.26，2026-09-22）

**采纳了「更保守」的形态：只做 dry-run 规划，不做自动执行。**

原建议是「工具内部串行调度 + 稳定等待 + 增量采集」。实际落地时**把执行环节去掉了** ——
工具只产出一份分批计划，导航仍由调用方按批发起。理由：

| 考量 | 说明 |
|------|------|
| **先定位真痛点** | 被打断的原因不是「导航太多」，而是**盲等**（不知道等多久、不知道进度）。一份带 `resumeFrom` 的计划就消掉了盲等，不必连执行一起接管 |
| **风险不对称** | 自动执行要在服务端维持长任务状态（job 生命周期、并发保护、MCP 重启丢 job）；而规划是**纯读**，失败无副作用 |
| **可复核** | 计划是静态数据，人可以扫一眼确认「这 143 条是不是我要测的」，再决定跑不跑。自动执行没有这个检查点 |
| **后续可增量** | 真要自动执行时，在 `batches` 之上加一层循环即可，计划的数据结构不用改 |

**落地形态**：`route_ops(action="plan_route_crawl", deadline_seconds=90, ...)`

| 关键设计 | 说明 |
|---------|------|
| **纯读保证** | 规划过程**零 CDP 求值**。验证方式是把 `runtime_eval` 换成会抛异常的桩再跑一遍 —— 靠「让它没法作弊」而不是靠读代码 |

| **估算口径显式化** | `estimatedSeconds` 是估算，口径写进返回的 `assumption`，不允许当精确预测 |
| **参数夹取** | `settle_ms`/`deadline_seconds`/`max_routes`/`start_from` 全部夹到合理区间，传怪值不会把工具搞坏 |
| **边界显式上报** | 计划为空、被截断、`settle_ms` 超 `deadline`、跳过分包、tabBar 清单为空 —— 全部进 `warnings` |

但接口全在跑，源码里必然有 baseUrl。改用正则 `https?://[a-zA-Z0-9.\-]+` 直接 grep 反编译产物，能提取出 374 条接口路径和多个域名。

**怀疑**：要么只做字面量匹配不支持正则，要么搜索范围不含 `app-service.js`。

**修复建议**：明确是否支持正则；增加 `is_regex` 参数；结果加 `maxBytes`。

**核查结论（2026-09-22 21:25）：现象可复现，但根因是调用方式 —— 工具侧已具备该能力。**

实测对照（对当前反编译产物）：

| 调用 | `hit_count` | 说明 |
|------|------------|------|
| `pattern="baseUrl"`（默认非正则） | **5** | 字面量搜索正常 |
| `pattern="baseUrl\|BASE_URL"`（默认非正则） | **0** | **复现了 P2-5 的现象** —— `\|` 被当字面量 |
| `pattern="baseUrl\|BASE_URL", is_regex=true` | **16** | 正则正常工作 |
| `pattern="https?://[a-zA-Z0-9.-]+", is_regex=true` | **48** | 正则正常工作 |
| `query="baseUrl"`（参数名写错） | 报错 `search_source 需要 pattern。` | **明确报错，不是静默忽略** |

→ **`is_regex` 参数本来就有**（P2-5 建议的「增加 is_regex 参数」**已实现**）；
→ 当时的 0 命中是**没传 `is_regex`** 造成的（`|` 被当字面量），属**调用方式问题**；
→ 参数名写错会**明确报错**，不会静默返回 0。

**判定：已在当前版本解决，无需改动。** 建议中的「结果加 `maxBytes`」仍可考虑（见 P2-4）。

### P2-6　反编译覆盖不到按需下载的分包

本次识别出 **5 个缺失分包**（`pages/other/`、`pages/zgfh/`、`pages/student/`、`pages/xcz/`、`pages/zgfhNew/`），但 `__APP__` 反编译产物只有 203 个文件。

（SKILL.md v2.24 已同步），也就是「覆盖不到」这件事**不再静默** ——

### P2-7　`find_sensitive_data_exposure` / `analyze_auth_surface` 检测面缺口

**现象**

```
analyze_auth_surface        → count: 0
find_sensitive_data_exposure → count: 0, credentialOnlyResponses: 0
```

而此时**手工已确认**：

- `GET /zsxc/t//api/common/infoConfig/getDefaultCfg` 在 `token: ""` 下返回 **200** 且泄露完整 `sysCfg`
- `POST /zsxc/t//api/common/infoConfig/getDqnf` 无 token 返回 200
- `GET /zsxc/t//api/common/infoConfig/getKlmcBySfdm` 无 token 返回 200
- storage 里有 14 年有效期 JWT

两个缺口：
1. **不扫描 storage**（与 P0-1 同源）。
2. **不把"空认证头 → 200"识别为认证缺失**。这是最典型的未授权访问信号，工具没有对应规则。

**修复建议**：新增规则——`token/cookie/Authorization 为空或缺失 且 statusCode == 200 且响应含业务数据` → 标记 `unauthenticated_access`（高优先级）。

**核查结论（2026-09-22 21:25）：缺口②是真缺陷，已修；缺口①不需要修。**

**缺口②：确证为假阴性，已修。**

`analyze_auth_surface` **本来就有**「缺认证 + 200」的规则（`missing_auth_candidate`），
但判据是 `AUTH_FIELD_RE.search(joined)` —— **只匹配字段名，不看值**。
于是 `{"token": ""}` 命中了字段名 → `has_auth=True` → **被跳过**。
小程序未登录时正是这种形态，所以「3 个接口在 `token: ""` 下返回 200」**全部漏报**。

离线验证（`scripts/verify_auth_surface.py`）：

| 用例 | 修复前 | 修复后 |
|------|--------|--------|
| `{"token": ""}` | ❌ **不上报** | ✅ 上报 |
| `{"Authorization": ""}` | ❌ **不上报** | ✅ 上报 |
| `{}`（无认证头） | ✅ 上报 | ✅ 上报 |
| `{"User-Agent": "..."}` | ✅ 上报 | ✅ 上报 |
| `{"token": "eyJhbGci..."}`（有效凭据） | ✅ 不上报（正确） | ✅ 不上报（正确） |

`count` 由 **2 → 4**。

**✅ 修复（v2.25，已完成并验证）**

新增 `McpRuntimeSession._contains_effective_auth()` —— 递归判据：
认证字段**必须值非空**才算「有凭据」，空串（`token: ""`）等同于没有凭据。
`analyze_auth_surface` 的 `has_auth` 改走它（`requestHeaders` / `query` / `requestBodyPreview` 三处都查）。
`scripts/verify_auth_surface.py` **5 passed / 0 failed**；冒烟 **60/60**。

> 这是与 P0-1 同类的**假阴性**：工具报告「没有未授权访问」，而真实的未授权访问就在它自己的数据里。

**缺口①：不需要修。**

`find_sensitive_data_exposure` 的定位是**响应体 PII**，凭据字段**故意不计入**
（`credentialOnlyResponses` 就是为此设的计数器，`count: 0` 未必是缺陷）。
storage 侧已由 `scan_sensitive_storage` 覆盖（P0-1 修复后实测 findings = 4）。
要求它也扫 storage 属**职责重叠**，不做。

### P2-8　`__routeNavigator.switchTabJson` 对非 tabBar 路由无显式失败反馈

`switchTabJson` 内部直接调 `wx.switchTab`，对非 tabBar 路由会失败，但 `runWxMethod` 的 `fail` 分支返回的 `ok:false` 在批量调度里容易被忽略（本次靠 try/catch + 回退 `reLaunchJson` 兜底）。

**修复建议**：`switchTabJson` 先校验路由是否在 `tabBarPages` 中，不在则直接返回 `{ok:false, reason:"not_a_tabbar_route"}`，不发起调用。

**核查结论（2026-09-22 21:25）：描述不准确，属低价值优化 —— 不改。**

`runWxMethod` 的 `fail` 分支**已经**返回 `ok:false` + `error`
（本轮修 P1-3 时专门确认过 `fail` 分支语义未动）。所以「没有显式失败反馈」**不成立** ——
反馈是有的，只是**批量调度里被忽略了**。

「先校验 `tabBarPages` 再调用」确实能省一次失败调用，但那是**优化**不是修缺陷，
且会让 `switchTabJson` 额外依赖 `fetchConfigJson` 的结果（多一层耦合）。**不改。**

## 附：环境侧（非工具缺陷，但由 P2-1 诱发）

连续 4 次相同参数的 `sleep 70`（用于等批量导航跑完）触发了上层 Agent 的**循环调用检测**，导致会话被强制中断。

根因不是 sleep 本身，而是 **P2-1**：工具缺少批量遍历原语，逼调用方用 `sleep` 做节奏控制。补上 `crawl_routes` 后该问题自然消失。
