# 验证方法论与成果口径（脱敏）

> 本文只描述**方法论、判据和结论口径**，不含任何具体目标、平台、域名、接口路径、
> 账号标识、真实数据样本或人员信息。所有案例均已抽象为类型与结构。

## 1. 为什么"对照实验"是唯一判据

自动化扫描最容易犯的错：把接口超时、JSON 空回显、通用模板当成漏洞，或把假阴性当"无漏洞"。
STRIKE 只认三类可证伪对照：

| 测试类型 | 对照设计 | 成立条件 |
|---|---|---|
| 越权（IDOR） | 本人 ID vs 他人 ID vs 随机 ID | 他人 ID 返回**确认属于他人**的数据，随机 ID 明确"不存在" |
| SQL 注入 | base vs payload 的时间中位数 / 报错特征 | 稳定超阈值的时间延迟，或明确的数据库语法错误（非业务/类型错误） |
| 认证缺陷 | 有凭证 vs 无凭证 vs 篡改凭证 | 响应差异可归因于凭证校验缺失，而非签名过期/WAF 拦截 |

**关键纪律**：
- 凭证被改后签名失效导致的空数据/鉴权错误 = 防护生效，**不是越权**；
- 必须区分"SQL 语法错误"与"业务参数错误"，前者才是注入证据；
- 缺阳性对照（比如找不到确认有效的他人标识）时，**如实标注"无法下结论"**，不写成"无漏洞"。

## 2. 签名/防重放场景的动态测试路线

很多小程序接口有实时签名（时间戳 + 设备签名 + 防重放），直接重放抓到的包必然失败。
绕过思路（不改算法、不逆向混淆）：

1. 在小程序运行时上下文加载业务模块；
2. 直接调用模块封装函数，**让小程序自己完成实时签名**；
3. 只替换想测的参数值；
4. 必要时用请求管线内的参数改写 hook，保持真实会话与签名上下文。

这条路线让"有签名防护"的接口也能做参数变异对照，而不是卡在"签名过期"就停。

## 3. 成果口径（按测试类型）

| 测试维度 | 覆盖方式 | 结论口径示例 |
|---|---|---|
| 静态面 | 反编译 + 全量规则扫描 | 规则数 / 命中数 / 高价值规则类别 |
| 动态面 | 路由遍历 + 请求采集 | 路由数 / API 请求数 / 不同接口数 |
| 接口鉴权 | 鉴权体系画像 | 凭证类型 / 设备签名 / 参数 encryption 层级 |
| 越权验证 | 3 组对照（本人/他人/随机） | 越权成立数 + 泄露数据敏感度评估 |
| 注入验证 | 报错/布尔/时间/编码绕过 | 阳性数 + 防护归因（WAF / 参数化） |
| 误报排除 | 逐项标注非漏洞原因 | 排除项清单 + 原因分类 |

## 4. 敏感度与定级：不夸大

一个常见问题是"越权成立"就等于高危。实际要看**泄露了什么**：

- 越权成立但数据只有低敏数值（如积分、等级模板值），且无身份信息、无真实资产 → 低危；
- 越权读到手机号/证件/地址等直接 PII，或真实资金/资产 → 中高危；
- 数据量大但无 PII（如历史运营记录、企业账户数据）→ 仍按敏感度而非字节数定级。

报告里必须写清：**实际返回的字段清单、哪些字段有真实差异、哪些是默认值**，
并明确纠正任何夸大的初版判断。

## 5. 诚实记录局限

- 被 WAF/频率封禁拦住的项目，标注"未测成"，不写"确认无漏洞"；
- 缺阳性对照的项目，标注"无法下结论"；
- 误判要纠正并留痕（例如把 403 误读成业务响应、把通用响应当成越权）。

## 6. 交付物结构建议

```
output/<appid>/
├── 阶段报告.md          # 全流程、结论、待办
├── 漏洞报告-*.md        # 每个确认漏洞：接口(脱敏)/对照/数据/定级
├── 注入测试报告.md      # 手法矩阵 + 阴性结论 + 防护归因
├── scan-result.json     # 静态扫描全量结果
└── requests-all.json    # 动态抓包原始数据（本地留存，不公开）
```

公开版只保留方法论与脱敏口径，原始抓包与含目标标识的报告**仅本地留存**。
